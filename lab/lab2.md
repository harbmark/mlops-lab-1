# Lab 2 — Model training and experiment tracking with MLflow

## Question 1 — What changed in `pyproject.toml` and `uv.lock`?

Running:

```
uv add mlflow torch torchvision scikit-learn
```

added four new dependencies to `pyproject.toml`: `mlflow`, `torch`, `torchvision`, `scikit-learn`.

**A GPU-specific wrinkle we hit:** plain `uv add torch torchvision` installed the **CPU-only** build (`torch==2.14.0+cpu`) by default, even though the machine has a real NVIDIA GPU (RTX 5070 Laptop). Confirmed with:

```python
import torch
print(torch.__version__)              # 2.14.0+cpu
print(torch.cuda.is_available())      # False
```

To get the CUDA build, we removed torch/torchvision and added an explicit index to `pyproject.toml`:

```toml
[[tool.uv.index]]
name = "pytorch-cuda"
url = "https://download.pytorch.org/whl/cu128"
explicit = true

[tool.uv.sources]
torch = { index = "pytorch-cuda" }
torchvision = { index = "pytorch-cuda" }
```

then re-ran `uv add torch torchvision`. This pulled a slightly **older** torch version than the CPU build (`2.11.0+cu128` instead of `2.14.0+cpu`) — PyTorch's CUDA wheel index lags behind PyPI's default. Confirmed working:

```python
print(torch.__version__)              # 2.11.0+cu128
print(torch.cuda.is_available())      # True
print(torch.cuda.get_device_name(0))  # NVIDIA GeForce RTX 5070 Laptop GPU
```

`uv.lock` grew substantially (thousands of new lines) to pin exact versions and hashes for the whole new dependency tree — mlflow, torch, torchvision, scikit-learn, and all their transitive dependencies.

**In simple terms:** `uv add` doesn't automatically give you the right build for your hardware — for GPU acceleration you may need to explicitly point uv at PyTorch's own package index.

## Question 2 — What is `--backend-store-uri` for? What is `--default-artifact-root` for? What's the difference between metadata and artifacts?

Started the tracking server with:

```
uv run mlflow server --host 127.0.0.1 --port 5000 --backend-store-uri sqlite:///mlflow.db --default-artifact-root ./mlruns
```

Checked what each flag actually produced on disk, right after starting the server (before any run existed):

```
Get-ChildItem mlflow.db   → exists immediately, 876544 bytes
Get-ChildItem mlruns      → does not exist yet
```

* **`--backend-store-uri`** — where mlflow stores structured **metadata**: experiment names, run IDs, params, metrics, tags, timestamps. Here, a SQLite file. It's created immediately because the server needs it to function, even with zero runs.
* **`--default-artifact-root`** — where mlflow stores the actual **files** a run produces: saved models, plots, any arbitrary logged file. Here, a folder. It's created *lazily* — only once a run actually logs something — which is exactly why `mlruns/` didn't exist until after the first training run finished.

**In simple terms:** metadata is small, structured, and drives the UI (tables, charts, filtering); artifacts are the large, unstructured *products* of a run, referenced by that metadata but stored separately.

## Question 3 — Why shouldn't `mlflow.db` and `mlruns/` be tracked by git or dvc?

Added both to `.gitignore`:

```
mlflow.db
mlruns/
```

**Why not git:** both are *generated output* from running code locally, not source of truth. They change every time training runs. Committing them would fill git history with noisy, constantly-changing binary/database diffs nobody can meaningfully review.

**Why not dvc either:** dvc is for versioning *fixed input data* everyone on a team needs the exact same copy of (like the Food-11 dataset). `mlflow.db`/`mlruns/` are the opposite — they're local experiment history specific to *this machine's* runs, not something a teammate should pull to reproduce your exact state. That job belongs to a shared mlflow tracking server (or just looking at the same UI together), not to dvc.

**In simple terms:** neither tool should track outputs that are regenerated by running your code — git skips it because it's noisy/derived, dvc skips it because it's not the kind of data dvc is for.

## Training the model

### Writing `train.py`

Created `./src/food11/train.py`, loading `food11_processed` or `food11_processed_mini` with `ImageFolder`, building a `resnet18` with its final layer replaced for 11 classes, accepting `--dataset`, `--epochs`, `--lr`, `--batch-size` as CLI args, and wrapping training in `mlflow.start_run()` with per-epoch metric logging.

**Note on dataset size:** confirmed directly (`Get-ChildItem data\food11_processed\training\Bread -File` → 33 files) that both `food11_processed` and `food11_processed_mini` only contain 33 images/category — a consequence of the sampling decision made in Lab 1 (raw data was reduced to 33/category before being processed). This means `mini` and `processed` are identical in this project; the "mini is faster to iterate on" framing in the lab doc doesn't apply here, since there was nothing left to trim.

### Two real bugs hit and fixed along the way

1. **`mlflow.pytorch.log_model(model, "model")` failed** with `input_example is required` for the `pt2` serialization format. Fixed by supplying an example input tensor:
   ```python
   example_input = next(iter(train_loader))[0][:1].cpu().numpy()
   mlflow.pytorch.log_model(model, "model", input_example=example_input)
   ```
2. **That still failed** with a device mismatch (`torch.FloatTensor` vs `torch.cuda.FloatTensor`) — the CPU-based example input couldn't be traced against the GPU-resident model under the strict `pt2` graph format. Fixed by falling back to the older, more permissive pickle format:
   ```python
   mlflow.pytorch.log_model(model, "model", input_example=example_input, serialization_format="pickle")
   ```
   This produced a working, fully saved model (confirmed: a 44,814,091-byte `model.pth` on disk), at the cost of a security warning (pickle can execute arbitrary code on load — a non-issue for local single-machine use, but worth knowing before sharing model files from untrusted sources).

## Question 5 — Difference between `log_param` and `log_metric`? Why does `log_metric` take `step` and `log_param` doesn't?

`log_param` records a value that's **fixed** for the whole run — learning rate, batch size, architecture — set once before training starts and never changes. `log_metric` records a value that **evolves during** training — loss, accuracy — and is logged repeatedly, once per epoch in our script.

`log_metric` takes a `step` argument because a metric is a *series* of values over time (one per epoch here) — mlflow needs to know which point in that series each value belongs to, so it can draw a chart. A param has no such series — it's a single, unchanging value, so there's nothing to index by step.

## Question 6 — Params, metric charts, and the logged model artifact — where does the model actually live on disk?

Opened the first successful run (`bemused-cub-661`) in the UI and confirmed directly:

* **5 Parameters**: `dataset=mini`, `epochs=5`, `lr=0.001`, `batch_size=32`, `model=resnet18`
* **4 Metrics**: `train_loss`, `val_loss`, `val_accuracy` (per-epoch, under the "Model metrics" tab as a chart), plus `test_accuracy` (single final value)
* **Logged models (1)** — confirmed present in the UI

**Where the artifact lives on disk:** initially guessed the old convention (`mlruns/<exp-id>/<run-id>/artifacts/model/`), but that path didn't exist. Checked directly with `Get-ChildItem mlruns -Recurse -Directory` and found this mlflow version (3.16.0) uses a **newer, model-registry-style layout**:

```
mlruns/1/models/m-c2e39cab10e5424696e6d1b4c0a9e095/artifacts/data/model.pth
mlruns/1/models/m-c2e39cab10e5424696e6d1b4c0a9e095/artifacts/data/pickle_module_info.txt
```

The model is stored under a separate top-level `models/` folder, keyed by its own model ID — independent of the run's own folder — with the run and model linked via metadata in `mlflow.db` rather than by directory nesting.

## Question 7 — Which learning rate gave the best `val_accuracy`? Is higher always better?

The **lowest** learning rate tested, `lr=0.0001`, gave both the best `val_accuracy` (0.587) and the best `test_accuracy` (0.623) — clearly not "higher is better." The opposite was true in these results: `lr=0.01` collapsed training almost entirely (`val_accuracy` dropped to ~0.085, and `val_loss` spiked to 19859 on epoch 0 — a clear sign of divergence, not learning).

With very little training data (363 images total, 33/category), a smaller learning rate lets the model fine-tune the pretrained ResNet18 weights gently rather than overshooting with large updates.

## Question 8 — Parallel coordinates plot: pattern across `lr`, `batch_size`, `val_accuracy`?

Selected all 5 successful runs, compared, and viewed the parallel coordinates plot with `val_accuracy` as the color metric (initially had to swap it in — it defaulted to `train_loss`).

**Pattern observed:** learning rate is clearly the dominant factor. The line for the lowest `lr` (0.0001) reaches the highest `val_accuracy` (~0.587) — colored red on the "good" end of the color scale. The line for the highest `lr` (0.01) drops to the lowest `val_accuracy` (~0.085) — the steepest, most dramatic trajectory on the whole plot. The three `lr=0.001` runs cluster tightly together in the middle (~0.43–0.47) regardless of `batch_size` — batch_size (32 vs 64) only produces a small secondary separation between otherwise-similar lines, nowhere near as dramatic as the learning-rate effect.
